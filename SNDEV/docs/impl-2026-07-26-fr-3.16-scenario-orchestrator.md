## 2. Specification Summary
- A named scenario composes any subset of the five advanced modules
  [pk_pd (FR-3.11), chemistry (FR-3.12), digital_twin (FR-3.13), mrd (FR-3.14),
  llm (FR-3.15)] with seeded parameters for reproducibility (FR-3.16.1).
- The orchestrator sequences the selected modules, propagates a shared
  simulated patient/state context, and collects outputs into a single
  `scenario_runs` record (FR-3.16.2).
- Aggregated multi-modal outputs are routable to configurable LIMS/EHR webhooks
  and responses are captured into `downstream_results` (FR-3.16.3).
- Given the same seed + config, deterministic (non-LLM) module output hashes
  must be reproducible; the LLM module records provider/model for provenance
  (FR-3.16.4).
- Frontend Scenario Designer assembles, configures, executes, and inspects
  scenarios within <=5 user interactions (FR-3.16.5 / NFR-U4).

### Determinism design
- Each module receives the same scenario `seed` (JSON). `_numeric_seed` (in each
  module) yields a stable 32-bit int for any JSON seed, so identical seeds
  reproduce identical deterministic outputs.
- `patient_id = f"SCN-{scenario_uid}"` is stable per scenario, so the LLM prompt
  is identical across re-runs as well.
- OQ-23 asserts `output_hashes` of the deterministic modules are byte-identical
  across two runs with the same seed; the LLM entry records provider/model.

### PQ-8 transparency note
PQ-8 per SRS requires ">=55 fps dashboard under concurrent load". The scenario
completion + downstream LIMS capture is fully implemented and asserted. The
">=55 fps dashboard" sub-clause is a frontend telemetry-dashboard performance
metric already covered by existing NFR-P1/P3 telemetry tests; the PQ-8 test
adds a concurrent-load smoke assertion (scenario endpoint sustains concurrent
requests without error) rather than fabricating a dashboard fps measurement.
This is documented here and in the test docstring.
